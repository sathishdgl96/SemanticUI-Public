# Manual pass — asking a report a question (sub-project 4)

**Date:** 2026-08-16
**Build:** `feature/foundation` at `64df359`
**Account:** `xriieim-eh01350` (`RC16948`, trial)
**Driver:** Chromium via Playwright, 1440×900

## What kind of pass this was

**Unstubbed.** The browser talked to the real backend, which talked to real
Snowflake. No `page.route` calls anywhere.

**The happy path could not be driven, and this record does not pretend
otherwise.** Cortex AI functions are unavailable on this trial account, so
every question returns `CORTEX_UNAVAILABLE`. What this pass verifies is that
the unavailable path behaves correctly — which, on this account, is the only
path a user will ever take.

## Steps and results

| # | Step | Result |
|---|---|---|
| 1 | Open a report | Loads |
| 2 | Ask button present in the header | Yes |
| 3 | Open the panel | Question box present and **enabled** |
| 4 | Ask "Which customer name has the highest customer count?" | Alert: *"Snowflake Cortex is not available on this account: AI function COMPLETE is not available for trial accounts."* |
| 5 | After the failure | Question box **still enabled** — not a dead panel |
| 6 | Close | Panel closes |
| 7 | 1440 / 1280 / 1024 / 768 / 390px | No horizontal overflow at any width |

Final state: **no page errors.** One logged `503 POST /ask`, which is the
correct response rather than a fault — it is the whole point of step 4.

The thing worth noting is that the user is told *why*. A generic "could not
answer that question", or a spinner that never resolves, would leave someone
on a trial account with no idea whether they had asked badly, hit a bug, or
lacked a feature. Snowflake's own sentence answers that in one line.

## Backend evidence

`backend/tests/integration/test_ask_it.py::test_cortex_availability_is_recorded`
runs against the real account and prints:

    [cortex] UNAVAILABLE: errno=399258 399258 (0A000):
    AI function COMPLETE is not available for trial accounts.

That test never fails — it records what the account offers, so the reason the
feature is dark is evidence rather than memory. The end-to-end question test
beside it **skips**, gated behind `SEMANTICUI_IT_CORTEX=1`, and will run once
Cortex is provisioned.

## What this pass did NOT cover

Stated plainly rather than implied by omission.

- **Any successful answer.** No question has ever been answered by a real
  model on this account. The whole success path — a real reply, parsed into a
  spec, validated, executed, rendered — is covered only by `FakeProvider`
  tests. That is a genuine gap and it stays open until Cortex is enabled.
- **Whether a real model actually produces a spec this catalog accepts.**
  This is the single most likely thing to be wrong when the feature is first
  switched on. `test_a_real_question_returns_a_spec_the_catalog_accepts`
  exists to answer it, and has never run.
- **Add as visual**, which needs an answer to pin.
- **A viewer's view of the panel** (no Add as visual), covered by unit tests
  only.

## When Cortex is enabled

1. Set `SEMANTICUI_IT_CORTEX=1` and run
   `pytest tests/integration/test_ask_it.py -m integration -v -s`.
2. Re-run this browser pass and record a real answer.
3. Expect the first real failure to be the model naming a field that does not
   exist. That is what `ASK_INVALID` is for, and the message names the field.

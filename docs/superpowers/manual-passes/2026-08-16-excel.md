# Manual pass — Excel export and live connection (sub-project 5)

**Date:** 2026-08-16
**Build:** `feature/foundation` at `84dca1f` plus the two fixes below
**Account:** `xriieim-eh01350` (`RC16948`, `AZURE_CENTRALINDIA`)
**Driver:** Chromium via Playwright, 1440×900, downloads enabled

## What kind of pass this was

**Unstubbed.** The browser talked to the real backend, which queried real
Snowflake. The downloaded workbook was then opened with `openpyxl` — a library
sharing no code with the writer — to check what Excel would actually see.

## What it found

**The server string we gave Excel would not have worked.**

The Connect panel showed `RC16948.snowflakecomputing.com`, taken from
`CURRENT_ACCOUNT()`. That is the account *locator*, and a bare locator only
resolves as a hostname in Snowflake's default region. This account is in
`AZURE_CENTRALINDIA`, so anyone following our instructions would have hit a
connection failure with nothing to tell them why.

Fixed by asking the connection for `CURRENT_ORGANIZATION_NAME()` and
`CURRENT_ACCOUNT_NAME()` and handing over the org-account form —
`XRIIEIM-EH01350` — which resolves everywhere. There is a fallback to the
stored locator for an older Snowflake without those functions, and tests for
both paths.

This is the whole argument for driving the real UI: every unit test passed,
because they asserted we returned *the account we had stored*, and the stored
one was the wrong kind.

**A horizontal overflow at 390px.** The builder header now carries Save, Move,
Ask, Excel, Connect live, Export and Import. It had never wrapped, and had only
fitted before because there were fewer buttons.

## Backend evidence

`test_export_it.py` runs against the real account and prints:

    [export] 6731 bytes, sheets=['Summary', 'CUSTOMER_NAME'], rows=50
    [connect-sql] accepted by Snowflake, 5 row(s)

The second line is the one worth having. The copyable SQL — including an
escaped `'O''Brien'` literal — was **executed against Snowflake and accepted**.
An inlined literal Snowflake rejected would otherwise have been discovered by a
user, inside Excel, with no error message from us.

## What this pass did NOT cover

Stated plainly rather than implied by omission.

- **Actually connecting Excel to Snowflake.** Excel is not installed in this
  environment. The SQL was verified to run against Snowflake directly, and the
  server string is now the form Snowflake's own documentation specifies, but
  nobody has completed the Data → Get Data → From Snowflake flow end to end.
  That is the remaining unknown in this feature.
- **A large export.** The test report has two rows. Truncation, the
  100,000-row cap and memory behaviour are covered by unit tests with a
  monkeypatched limit, not by a real large result.
- **A formula-injection payload arriving from real Snowflake data.** The
  defence is covered by unit tests that write each dangerous prefix and read
  the cell type back; no warehouse column here happens to contain one.
- **A partially-forbidden export in the browser.** Covered by
  `test_a_forbidden_visual_does_not_lose_the_whole_workbook`, not driven with
  two real Snowflake roles.
